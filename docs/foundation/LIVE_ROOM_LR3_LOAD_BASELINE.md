# Live Room LR-3 load baseline

**Дата:** 2026-11-26. **Статус:** измерен baseline; это диагностические
числа, не production SLO и не продуктовая приёмка.

## Среда

- WSL2, Linux 6.18.58.1, **4 vCPU**, 3.8 GiB RAM, swap 4 GiB (на момент
  прогонов использовалось ~3.4 GiB swap).
- Docker Compose dev-lite: `web` limit **1 GiB**, `db` limit **768 MiB**;
  PostgreSQL 18, Python 3.14, Django 5.2.
- Polling interval **1200 ms**; команды и чтение идут через сервисный
  слой Django в одном процессе с независимыми DB-соединениями.
- Для 4-player baseline `DB_POOL_MAX` по умолчанию (8); для 8/12 и
  нескольких комнат — 32/48, чтобы не измерять исчерпание общего пула
  одного процесса. HTTP/nginx в эти числа не входят; browser E2E —
  отдельный слой доказательств.
- Команда: `manage.py room_loadtest --rooms R --players P --seconds S
  --poll-ms 1200`; создаёт комнаты с активной игрой и отдельную lobby-
  комнату для команд ready, затем удаляет свои данные.

## Предлагаемые диагностические budgets

Для reference-профиля **1 комната × 12 игроков, poll 1200 ms, 30 s,
DB pool 48**:

- read p95 ≤ **350 ms**, p99 ≤ **750 ms**;
- command p95 ≤ **600 ms**, p99 ≤ **900 ms**;
- неожидаемых ошибок — **0**;
- `pg_stat_activity` lock waiters ≤ **2** на сэмпл;
- web CPU ≤ **150%** одного ядра, RSS ≤ **512 MiB**; db RSS ≤ **256 MiB**.

Для **3 комнат × 4 игрока**: read p95 ≤ **300 ms**, p99 ≤ **500 ms**,
ошибок 0. Это внутренние пороги для повторного baseline в той же среде,
не обещание production SLA. Более строгие числа без HTTP/продового
железа были бы выдумкой.

## Решение по `read_room`

Текущий `read_room` берёт `select_for_update` на каждом poll, обновляет
`last_seen` не чаще 10 s и делает stale sweep. На измеренном профиле
12 игроков одна комната даёт p95 180–304 ms, p99 499–507 ms, 0 ошибок,
lock waiters 0–2 и ~7 SQL на чтение. Это укладывается в polling 1200 ms
и не показывает деградации, требующей усложнения read/mutation path.
Оптимизация **не внедрялась** — по правилу «сначала измерение».
Пересмотреть при p95 > 350 ms, росте числа комнат или переходе на HTTP
нагрузку с несколькими процессами.

## Ограничения

- WSL2 с активным swap и 4 vCPU; цифры не переносятся на production
  hardware.
- Измеряется сервисный слой в одном процессе, а не gunicorn + nginx +
  TLS; сетевой вклад не включён.
- `DB_POOL_MAX` выше default для части прогонов, иначе измерялся бы не
  row lock, а ожидание общего пула.
- Нет длительного soak-теста (часы), multi-host, Redis/Celery под
  одновременной нагрузкой и реальных мобильных сетей.
