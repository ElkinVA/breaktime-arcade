## 1. Архитектурное резюме

Целевая схема сохраняет нормативный инвариант: игра выполняется в iframe на
отдельном origin, не получает cookies/билет/данные пользователя, а связь с
платформой идёт только через официальный SDK и postMessage. Платформа
остаётся единственным доверенным вычислителем результата, рекордов, времени
и доверия.

Ключевое разделение:

1. **Игра** — недоверенный код. Она может отправлять только сообщения App F.
2. **BA SDK** — официальный адаптер внутри iframe; проверяет сообщения
   родителя и не даёт игре прямого доступа к API/portal cookies.
3. **Host protocol** — код родительской страницы; первый барьер проверки
   `event.source`/`event.origin`, сессии, `requestId`, схемы, rate limit и
   состояния; не является окончательным авторитетом.
4. **Django API/сервисы** — окончательная авторизация, проверка владения
   сессией, результата, времени, EventLog, идемпотентности и рекордов.
5. **PostgreSQL** — источник истины для сессий, результатов, рекордов,
   storage и аудита; ограничения должны защищать инварианты даже при ошибке
   сервиса.

Ни один клиентский `score`, `durationMs`, `seed`, `trustLevel`, `mode` или
`clientMeta` не считается доверенным. `sessionId` — не bearer-token: он
публичен в fragment/сообщениях, а владение подтверждается cookie/CSRF
родительской сессии и серверной проверкой.

`portal.test:8443` и `*.games.test:8443` на схеме — dev-пример из
`BA-ENV-1.1_DRAFT`/фактической среды, не утверждённые production-домены.
Production-домены, TLS и CDN остаются решением владельца.

## 2. Целевая схема взаимодействия

```text
Browser, portal origin (portal.test:8443 / production portal)
┌────────────────────────────────────────────────────────────────────┐
│ Django page /play/                                                 │
│  - create session via same-origin POST /api/v1/sessions             │
│  - keep ticket + binding_nonce in page memory (never in iframe URL) │
│  - render iframe with #p=<portal-origin>&s=<sessionId>              │
│  - host_protocol.js: message listener, origin/source/session checks │
│  - same-origin fetch to /api/v1/... with cookies + CSRF             │
└───────────────┬────────────────────────────────────────────────────┘
                │ postMessage (source/origin/session/requestId/schema)
┌───────────────▼────────────────────────────────────────────────────┐
│ Game iframe, separate origin <host_label>.<games-domain>            │
│  - sandbox allow-scripts [allow-same-origin] [allow-pointer-lock]    │
│  - no portal cookies, ticket, user identifiers                      │
│  - official ba-sdk.js; game code uses only BreaktimeArcade API      │
└───────────────┬────────────────────────────────────────────────────┘
                │ SDK is the only bridge
┌───────────────▼────────────────────────────────────────────────────┐
│ Django API + services                                              │
│  sessions/tickets/context/heartbeat/result/leaderboard/storage      │
│  validation, verifier, idempotency, rate limits, audit              │
└───────────────┬────────────────────────────────────────────────────┘
                │ transactions, constraints, locks
┌───────────────▼────────────────────────────────────────────────────┐
│ PostgreSQL 18: GameSession, GameResult, LeaderboardEntry,           │
│ GameStorage, GamePlayCredit, GameDailyStats, SecurityEvent          │
│ Redis: rate-limit counters, short-lived session/message state       │
└────────────────────────────────────────────────────────────────────┘
```

### 2.1. Ответственность компонентов

| Компонент | Отвечает | Не отвечает |
|---|---|---|
| Игровой iframe | игровой цикл, отображение, собственный eventLog, вызов SDK | доверие результату, доступ к API/portal cookies, выбор mode/seed/trust |
| BA SDK | API `init/context/ready/t/submitResult/leaderboard/storage/newSession/exit/fail`, проверка host-сообщений, таймауты/ретраи | серверная авторизация, начисление рекордов, проверка anti-cheat |
| Host protocol | iframe lifecycle, `event.source`/`event.origin`, текущая сессия, `requestId` LRU, schema/rate/state pre-check, вызов same-origin API | окончательное доверие результату, выдача билета в iframe, обход серверных проверок |
| Django API/services | создание/активация/ heartbeat/ result/ close, ownership, идемпотентность, EventLog, verifier, leaderboard, storage | исполнение игрового кода, CORS-доступ из iframe |
| PostgreSQL | транзакции, уникальность, FK/CHECK, история, рекорды, retention | проверка браузерного origin, UI-поведение |
| Redis | rate-limit, краткоживущие счётчики; не источник истины | хранение результата/сессии как единственной копии |

## 3. Реестр проектных решений

### APPF-DEC-001 — границы доверия

- **Класс:** [TZ] §2.4, §2.12.4, §2.14.3 + [PROP].
- **Вопрос:** кому доверять сообщения, контекст и результат.
- **Источники:** BA-PLAT-4.2 §2.4, §2.12.4, §2.14.3; BA-GAME-2.2 §4, §6.
- **Рекомендация:** считать игру и SDK недоверенными; host protocol —
  платформенным, но не окончательным авторитетом; все state-changing
  операции проверять в Django/БД. Игра не получает ticket, cookies, email,
  логин, токены и идентификаторы пользователя. Прямой `postMessage` из
  игрового кода запрещён; официальный SDK заменяет `js/ba-sdk.js`.
- **Альтернативы:** доверять SDK/клиенту; разрешить iframe прямой API;
  выполнять игру на сервере. Все три противоречат ТЗ/архитектуре.
- **Последствия:** больше серверных проверок и задержки; но результат и
  рекорды не зависят от клиентского доверия.
- **Приоритет:** Blocker. **Требует владельца:** Нет (нормативный инвариант).

### APPF-DEC-002 — iframe, fragment и билет

- **Класс:** [TZ] §2.4.3, §2.12.2 + [DRAFT].
- **Вопрос:** какие данные попадают в URL iframe и как привязывается сессия.
- **Источники:** BA-PLAT-4.2 §2.4.3, §2.12.2; `SESSION_ID_PROTOCOL.md`.
- **Рекомендация:** URL iframe содержит только несекретные
  `#p=<portal-origin>&s=<sessionId>`; ticket и binding nonce остаются в
  памяти родительской страницы. iframe создаётся с
  `sandbox="allow-scripts allow-same-origin"` (плюс `allow-pointer-lock`
  только при `capabilities.pointerLock=true`), `referrerpolicy=no-referrer`;
  на игровом хосте нет `X-Frame-Options`, изоляция — `frame-ancestors`.
  `targetOrigin` для postMessage — точный origin игры, никогда `*`.
- **Альтернативы:** ticket в query/fragment; wildcard targetOrigin; iframe на
  поддомене портала. Запрещены ТЗ.
- **Последствия:** ticket не утекает в игру; sessionId не является секретом.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ).

### APPF-DEC-003 — официальный SDK и версия

- **Класс:** [TZ] §2.14.3, §2.25 + [DRAFT].
- **Вопрос:** как игра получает SDK и как проверяется совместимость.
- **Источники:** BA-PLAT-4.2 §2.14.3; BA-GAME-2.2 §6; `BA-SDK-1.1_DRAFT.md`.
- **Рекомендация:** при публикации всегда заменять `js/ba-sdk.js` официальной
  реализацией; файл из ZIP не исполняется и не считается доверенным.
  Проверять `manifest.sdkVersion` (semver-range) и `manifest.protocol=1`;
  несовместимость — `V_SDK_INCOMPATIBLE` на этапе импорта, не в runtime.
- **Альтернативы:** использовать SDK из ZIP; загружать SDK с CDN; разрешить
  game-code обращаться к API напрямую. Несовместимы с §2.14.3/§2.4.
- **Последствия:** official SDK становится частью runtime_hash; отчёт
  инъекции обязателен.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ), но контракт SDK
  требует утверждения/оригинала.

### APPF-DEC-004 — серверный контекст и seed

- **Класс:** [TZ] §2.12.1, §2.12.6 + [PROP].
- **Вопрос:** кто задаёт mode, seed, trustLevel и параметры счёта.
- **Источники:** BA-PLAT-4.2 §2.12.1, §2.12.6, §2.23; BA-GAME-2.2 §6.
- **Рекомендация:** `sessionId`, `seed`, `mode`, `trustLevel`, score/limits и
  gameVersion создаёт/выбирает сервер. Клиентские mode/seed/trustLevel
  игнорируются. Seed — криптографически случайная строка, уникальная для
  сессии; `ba:context` доставляет её игре, но не позволяет менять.
- **Альтернативы:** seed от клиента; mode из query; trustLevel из manifest.
  Противоречат §2.12.1/§2.12.6.
- **Последствия:** replay/детерминизм проверяемы только относительно
  серверного seed.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ).

### APPF-DEC-005 — уровни доверия и верификатор

- **Класс:** [TZ] §2.12.6 + [DRAFT].
- **Вопрос:** как назначается trustLevel и что означает заявка манифеста.
- **Источники:** BA-PLAT-4.2 §2.12.6, §2.22 (`verifier_slug`,
  `trust_level_max`, `leaderboard_only_verified`).
- **Рекомендация:** `manifest.leaderboard.claimedVerification` — только
  заявка. Уровень назначает сервер после эвристик/верификатора; значение
  клиента игнорируется. `client_reported` — базовый; `heuristic_validated` —
  расширенные проверки; `replay_verified` — успешный серверный replay;
  `server_authoritative` зарезервирован. Подозрительное — quarantine +
  `SecurityEvent`, не автоматический рекорд.
- **Альтернативы:** доверять claimedVerification; присваивать уровень SDK.
  Противоречат §2.12.6.
- **Последствия:** возможны ложные quarantine/отказы; нужна модерация.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ), но правила
  verifier для конкретных игр — CRM/владелец.

### APPF-DEC-006 — guest/preview/autotest isolation

- **Класс:** [TZ] §2.1, §2.8, §2.12.1, §2.12.5 + [GAME] §6.
- **Вопрос:** какие режимы влияют на рекорды, статистику, время и доверие.
- **Источники:** BA-PLAT-4.2 §2.1, §2.8, §2.12.1, §2.12.5; BA-GAME-2.2 §6.
- **Рекомендация:** `guest` не сохраняет `GameResult`, не попадает в
  leaderboard и не переносится в аккаунт; `preview` ведёт себя как guest и
  не влияет на агрегаты; `autotest` — `is_test=true`, не влияет ни на что,
  кроме служебного раздела проверок. Для preview/autotest использовать
  служебный аккаунт/CRM с 2FA; не impersonate реального пользователя.
- **Альтернативы:** сохранять гостевые результаты; учитывать preview в
  популярности; разрешить autotest от любого пользователя. Запрещены ТЗ.
- **Последствия:** ниже конверсия в рекорды у гостей, но соблюдены
  продуктовые инварианты.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ).

### APPF-DEC-007 — канонический envelope

- **Класс:** [TZ] §2.12.4, Приложение F + [OWNER] OD-FOUND-001 + [DRAFT].
- **Вопрос:** имена и обязательность полей сообщения.
- **Источники:** BA-PLAT-4.2 §2.12.4, Приложение F; BA-GAME-2.2 §6;
  `schemas/messages/_envelope.json`; `SESSION_ID_PROTOCOL.md`.
- **Рекомендация:** ровно `{source, protocol, type, requestId, sessionId,
  payload}`; `protocol=1`; `requestId`/`sessionId` — UUID; `payload` — object.
  Внешний JSON всегда `sessionId`; Python/БД — `session_id`. Лишние поля
  envelope отклонять; `payload` — по схеме типа.
- **Альтернативы:** поддерживать legacy `session_id` снаружи; разрешать
  дополнительные envelope-поля; сделать payload произвольным. Legacy не
  решён; дополнительные поля ослабляют контроль.
- **Последствия:** строгая совместимость; старые примеры ТЗ с `session_id`
  остаются расхождением C-001.
- **Приоритет:** Blocker. **Требует владельца:** Да — утверждение BA-SDK-1.1
  и решение по legacy `session_id`.

### APPF-DEC-008 — origin/source

- **Класс:** [TZ] §2.12.4 + [PROP].
- **Вопрос:** как отличить сообщение своего iframe от чужого.
- **Источники:** BA-PLAT-4.2 §2.12.4; `MESSAGE_PROTOCOL.md` §4.
- **Рекомендация:** проверять в порядке: `event.source ===
  iframe.contentWindow`; точный `event.origin` (scheme+host+port) из
  `Game.host_label`/активного домена; `data.source === "ba-sdk"`;
  `data.protocol === 1`; `data.type` allowlist; `data.sessionId` текущей
  сессии; `requestId`; schema; rate; state. Не использовать `origin.endsWith`,
  regex или `source`-строку вместо `event.source`. Fail closed.
- **Альтернативы:** проверять только `event.origin`; проверять только
  `event.source`; разрешить `*`. Недостаточны/запрещены.
- **Последствия:** необходимо хранить точный origin игры в БД и учитывать
  dev-порт 8443.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ).

### APPF-DEC-009 — sessionId и requestId

- **Класс:** [TZ] §2.12.4 + [OWNER] OD-FOUND-001 + [DRAFT].
- **Вопрос:** какие UUID допустимы и как предотвращается replay.
- **Источники:** BA-PLAT-4.2 §2.12.4; `SESSION_ID_PROTOCOL.md`;
  `MESSAGE_PROTOCOL.md`.
- **Рекомендация:** `sessionId` — UUID текущей сессии; `requestId` — UUID
  RFC 4122 (v4/v7). Родитель хранит LRU на 512 `requestId` на сессию;
  повтор `requestId` игнорируется; при `ba:newSession` LRU очищается.
  `requestId` не заменяет `Idempotency-Key` результата и не является
  секретом.
- **Альтернативы:** глобальный LRU; UUID без проверки версии; использовать
  `requestId` как idempotency key результата. Глобальный LRU мешает
  параллельным сессиям; idempotency результата имеет отдельный ключ.
- **Последствия:** replay-защита ограничена 512 последними сообщениями и
  временем жизни сессии; этого достаточно для протокола, но не для
  долговременной дедупликации результата.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ/owner naming).

### APPF-DEC-010 — типы и направления

- **Класс:** [TZ] Приложение F + [DRAFT].
- **Вопрос:** какие типы разрешены и в каком направлении.
- **Источники:** BA-PLAT-4.2 Приложение F; `MESSAGE_PROTOCOL.md` §2;
  `schemas/messages/*.json`.
- **Рекомендация:** 14 типов; игра→host: hello, submit, leaderboard,
  storage, newSession, exit; host→game: context, result, leaderboard:data,
  storage:data, session, pause, resume; `ba:error` — оба направления.
  Направление проверяется по фактическому `event.source`, затем по
  `source`/схеме. Неизвестный тип после базовых проверок — молча
  игнорировать и логировать; не менять состояние и не отправлять
  `ba:error` неизвестному источнику.
- **Альтернативы:** отвечать ошибкой на любой неизвестный тип; разрешить
  типы без allowlist. Ошибка создаёт oracle/шум; allowlist обязателен.
- **Последствия:** расширение протокола требует нового типа/схемы и
  обратной совместимости.
- **Приоритет:** Blocker. **Требует владельца:** Да — для новых типов
  (`autotest:finish`, `myBest`, `fail`) см. APPF-DEC-025/027/045.

### APPF-DEC-011 — JSON Schema и неизвестные поля

- **Класс:** [TZ] Приложение F + [DRAFT] + [PROP].
- **Вопрос:** где и насколько строго валидировать JSON.
- **Источники:** `schemas/messages/*.json`, `schemas/eventlog.json`,
  `apps/core/contracts.py`.
- **Рекомендация:** использовать JSON Schema 2020-12 на сервере и в SDK;
  envelope — strict; game→host payloads — strict (`additionalProperties:
  false`); host→game `ba:context`/`ba:session` могут быть additive, SDK
  обязан игнорировать неизвестные поля. Валидировать до dispatch; ошибки

### APPF-DEC-016 — модель состояний

- **Класс:** [TZ] §2.12.1 + [OPEN].
- **Вопрос:** как представить `paused` и `failed`, которых нет в
  нормативном перечне.
- **Источники:** BA-PLAT-4.2 §2.12.1 (`created → active → finished |
  expired | aborted`); BA-GAME-2.2 §6; `ba_schema.sql` `gameplay_session`.
- **Рекомендация:** сохранить нормативные persisted-состояния
  `created`, `active`, `finished`, `expired`, `aborted`. `paused` — не
  отдельное состояние БД, а операционный флаг/интервал внутри `active`
  (`pause_started_at`/`resumed_at` или telemetry), потому что добавление
  `paused` в state machine меняет нормативный контракт. `failed` — не
  отдельное состояние: это `aborted` с `reason` (game_error, server_error,
  verification_error, replaced). Если владелец хочет `paused`/`failed` как
  persisted states, требуется явное изменение модели в ТЗ.
- **Альтернативы:** добавить `paused` и `failed` в БД; отображать paused как
  `expired`; не различать normal/abnormal. Первое конфликтует с §2.12.1;
  второе теряет семантику; третье ухудшает аналитику.
- **Последствия:** `paused` не влияет на TTL/credited_ms; сервер считает
  время по heartbeat, а не по клиентской паузе.
- **Приоритет:** Blocker. **Требует владельца:** Да — подтвердить
  отображение paused/failed.

- **Класс:** [FACT] SQL + [TZ] §2.10.5 + [OPEN].

### APPF-DEC-042 — DB-008: фактический размер JSONB storage

- **Класс:** [TZ] §2.22 + [FACT] SQL.

- **Источники:** `ba_schema.sql:454-468`; BA-PLAT-4.2 §2.22.
- **Факт:** `bytes` — обычное integer, CHECK только `<=65536`; сервис

- **Альтернативы:** оставить CHECK на bytes; проверять только сервис;
  `pg_column_size` (не то же, что UTF-8 JSON). DB-check + сервис.
- **Последствия:** возможны отказы больших документов; нужно
  канонизировать JSON.
- **Приоритет:** High. **Требует владельца:** Нет (TZ).

### APPF-DEC-043 — App J и SQL-зависимости

- **Класс:** [TZ] Приложение J + [FACT] mapping/DDL.
- **Вопрос:** какие расхождения нужно закрыть до миграций App F.
- **Источники:** `APP_J_FIELD_MAPPING.md`; `ba_schema.sql`;
  BA-PLAT-4.2 Приложение J.
- **Факт:** `GameResult.game_id` — техническое дополнение; `GameTranslation
  .name` 128 vs 60; `GameVersion` immutable vs user FKs; `GameStorage`
  bytes; `GameSession` mode/subject; удаление пользователя.
- **Рекомендация:** до App F-миграций принять APPF-DEC-035…042 и
  зафиксировать в SQL/Django-моделях; не смешивать исправления с
  реализацией протокола. Импорт/CRM-мастер не входят в App F, но поля
  `Game`/`GameVersion` должны быть готовы.
- **Альтернативы:** отложить DB-исправления до этапа 4 (риск переделки
  результатов/рекордов); исправлять после первых данных (дороже).
- **Последствия:** сначала контракт/DDL, затем модели/миграции, затем API.
- **Приоритет:** Blocker. **Требует владельца:** Да — по пунктам,
  отмеченным выше.

| Исправление | До App F? | Обоснование |
|---|---|---|
| DB-001 удаление/XOR (APPF-DEC-035) | **Да, blocker** | иначе удаление аккаунта ломает result/session |
| DB-002 result↔session (036) | **Да, blocker** | иначе результат может ссылаться на чужую игру/субъект |
| DB-003 leaderboard↔result (037) | **Да, blocker** | иначе рекорд расходится с результатом |
| DB-007 mode↔subject (041) | **Да, blocker** | иначе guest/user/preview попадают в неверные агрегаты |
| DB-008 storage bytes (042) | **Да, blocker** | иначе квота 64 КиБ обходится |
| DB-006 GameVersion immutability (040) | **Да, до миграций/удаления** | trigger конфликтует с `ON DELETE SET NULL` |
| DB-004 identifier reuse (038) | **До импорта/удаления игр; можно параллельно** | App F не создаёт игры, но правило immutable |
| DB-005 name length (039) | **До импорта/App J; можно отложить от runtime App F** | не влияет на postMessage/сессии |

Таким образом, DB-001/002/003/006/007/008 должны быть закрыты до
App F-миграций; DB-004/005 можно вести параллельно с импортёром, но нельзя
оставлять открытыми к приёмке App J/каталога.

### APPF-DEC-044 — тестовая матрица

- **Класс:** [TZ] §2.26 + [PROP].
- **Вопрос:** какие проверки обязательны до приёмки.
- **Источники:** BA-PLAT-4.2 §2.26; BA-PLAT-4.2 §2.12–§2.14.
- **Рекомендация:** unit (валидаторы, state machine, idempotency, seed,
  duration, score, EventLog), integration/API (сессии, guest, result,
  leaderboard, storage, 403/409/413/429), browser/iframe (playwright:
  origin/source, guest, pause/resume, newSession, exit, CSP/no XFO, no
  cookies), security (чужой iframe, replay, stale session, forged
  source/origin, oversized payload, rate limit, CSRF/CORS), concurrency
  (100 параллельных результатов, две вкладки, active limit 3, leaderboard
  upsert), retry/idempotency (same/different key, timeout), negative
  (invalid schema, wrong direction, unknown type, bad eventLog, bad seed,
  expired/aborted).
- **Альтернативы:** только unit; только happy path; моки вместо
  PostgreSQL/iframe. Недостаточны.
- **Последствия:** нужны Playwright и отдельная тестовая игра; тесты
  должны проверять реальное поведение, не только наличие схем.
- **Приоритет:** Blocker. **Требует владельца:** Нет (TZ).

### APPF-DEC-045 — критерии приёмки App F

- **Класс:** [TZ] §2.26, §2.12–§2.14 + [PROP].
- **Вопрос:** когда App F считать готовым.
- **Источники:** BA-PLAT-4.2 §2.26, §2.12–§2.14, Приложение F.
- **Рекомендация:** приёмка только при:

1. Утверждённом BA-SDK-1.1/BA-ENV-1.1 (или официально согласованном
   эквиваленте) и выбранном/согласованном BA-GAME-2.2.
2. Все 14 типов + недостающие (`myBest`, `autotest:finish`, `fail`)
   имеют утверждённые схемы и направления.
3. Origin/source/ticket/sessionId/requestId/schema/rate/state проверяются
   на реальном iframe; чужой iframe не проходит.
4. Все переходы жизненного цикла и TTL подтверждены интеграционными
   тестами.
5. Result validation, idempotency, 100 параллельных результатов, guest,
   preview/autotest, leaderboard, storage, EventLog/replay — зелёные.
6. SQL constraints и App J согласованы; миграции проверены
   `makemigrations --check` и `migrate --plan`.
7. Browser/E2E, security, load S2/S3; 0 Blocker/0 Critical, ≤5 Major с
   планом, coverage доменных модулей ≥70%.
8. Нет CORS, cookies в iframe, ticket в URL, X-Frame-Options на игровом
   хосте; CSP проверен.

- **Альтернативы:** закрыть по наличию кода/схем; принять DRAFT как
  окончательный. Запрещено.
- **Последствия:** App F нельзя считать готовым до owner approval.
- **Приоритет:** Blocker. **Требует владельца:** Да (утверждение
  контрактов/BA-GAME).

## 6. Рекомендуемый порядок реализации

1. **Контракты:** владелец утверждает BA-SDK-1.1/BA-ENV-1.1 или официально
   ограничивает scope; выбирает/утверждает BA-GAME-2.2. Зафиксировать
   решения APPF-DEC-007…014, 016/017, 025, 027, 030, 033.
2. **SQL/App J:** исправить APPF-DEC-035…042 в проектной схеме; согласовать
   `GameResult.game_id`, name length, mode/subject, storage bytes; только
   после этого создавать Django-модели/миграции.
3. **Модели/сервисы:** `GameSession`, ticket/hash, seed, context, state
   machine, heartbeat, result, leaderboard, storage; транзакции и
   constraints; admin/CRM read-only.
4. **API:** sessions create/activate/heartbeat/result/close; leaderboard;
   storage; same-origin, CSRF, deny-by-default; rate limits; no CORS.
5. **Host protocol:** iframe lifecycle, exact origin/source, targetOrigin,
   requestId LRU, schema/rate/state pre-check, same-origin fetch.
6. **SDK:** official `ba-sdk.js`; init/context/ready/t/on/submit/leaderboard/
   storage/newSession/exit/fail; timeouts/retries; no direct postMessage.
7. **Result/EventLog/verifier:** server validation, idempotency, eventlog,
   replay, trust/quarantine; leaderboard transaction.
8. **UI/iframe:** play page, guest/preview/autotest, pause/resume/newSession/
   exit, errors; CSP/sandbox/no XFO.
9. **Tests:** unit/integration/API/browser/security/concurrency/retry/
   negative; real PostgreSQL; Playwright; load S2/S3.
10. **Rollout:** feature flags; staging only after approval; production not
    part of this task. No migration before schema review.

## 9. Итог

Документ предлагает целевую архитектуру и конкретные решения, но **не
закрывает** вопросы, требующие владельца: BA-SDK/ENV, BA-GAME, `ba:error`,
`myBest`, `autotest:finish`, paused/failed, лимиты сообщений, EventLog
transport, удаление пользователя и DB-001…008. До утверждения этих
пунктов реализация App F будет либо нарушать ТЗ, либо закреплять
неутверждённые DRAFT-правила.
