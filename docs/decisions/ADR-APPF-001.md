# ADR-APPF-001 — закрытие контрактов App F и технические решения Architect

**ID:** ADR-APPF-001
**Дата:** 2026-11-22
**Статус:** **ACCEPTED — technical/internal (Architect)**; внешние
юридические, платные, инфраструктурные и продуктовые действия не выполнялись.
**Полномочия:** `OD-AUTONOMY-006` в `OWNER_DECISIONS.md` — Architect уполномочен
принимать технические и продуктовые решения App F/Browser Arcade в пределах
BA-PLAT-4.2, оформляя их ADR.
**Приоритет источников:** ТЗ (BA-PLAT-4.2, BA-GAME-2.2) > фактический код >
этот ADR. ADR не переписывает ТЗ, не публикует юридические тексты, не
подключает платные сервисы и не выполняет внешние/необратимые действия.

## 0. Назначение и границы

Этот ADR закрывает контрактную неопределённость, которая блокировала
реализацию App F: выбор BA-GAME-2.2, внутреннюю приёмку BA-SDK-1.1 и
BA-ENV-1.1, решения по лимитам сообщений и `sessionId`, DB-001…DB-008,
доверию/EventLog/storage/leaderboard, retention, ролям/2FA/step-up,
email-адаптеру и требованиям к production.

Решения ниже — **внутренние технические решения Architect**, а не решения
владельца и не замена:

- юридической проверки Terms/Privacy, DSA/EN 301 549, GDPR-оснований и
  формулировок согласий (внешнее действие владельца/юриста);
- выбора и подключения платного/внешнего провайдера (email, S3/CDN, Sentry,
  CAPTCHA, хостинг);
- регистрации доменов, DNS/TLS, получения секретов и production deploy;
- продуктовой приёмки срезов App F владельцем;
- изменения исходного текста BA-PLAT-4.2 или BA-GAME-2.2.

Если решение ниже расходится с ТЗ, действует ТЗ, а расхождение фиксируется
как остаток. Ни одно решение не является «временным контрактом, выданным за
нормативный»: временные ограничения помечены явно.

## 1. Реестр решений

### D1. Канонический BA-GAME-2.2 — вариант A

**Решение.** Каноническим текстом BA-GAME-2.2 для внутренней разработки
принимается **вариант A** — раздел `# ДОКУМЕНТ 2 — BA-GAME-2.2` в
`technical_specification/ts_site.txt`. Вариант B (`ts_game.txt`) остаётся
историческим эквивалентом; он является собственным подмножеством A.

**Основание.** Машинное сравнение (`docs/audits/BA-GAME-2.2_COMPARISON.md`)
не нашло содержательных противоречий: §1–§17 совпадают построчно, а
дополнительный блок A повторяет уже действующие требования BA-PLAT-4.2
(`capabilities.storage:"local"` запрещён, `catalog.description` 1600,
`id`-привязка хоста, гостевая нормализация SDK 1.1, эпохи рекордов,
исключение служебных режимов из агрегатов). Процессная заметка
«Следующий шаг» в контракт не входит.

**Последствия.**
- Контрактным baseline для manifest/UX/игровых проверок считается A.
- Исходные файлы ТЗ не изменяются; B не удаляется.
- Юридические формулировки из A (16+, резерв никнейма 24 месяца, DSA/EN 301
  549) остаются требованием внешней юридической проверки.
- Реальных игровых ZIP и контрактов с игровой командой это решение не
  создаёт.

### D2. BA-SDK-1.1 v1.1.0 — внутренняя приёмка

**Решение.** `docs/contracts/BA-SDK-1.1_v1.1.0.md` принимается как
**внутренний технический контракт SDK 1.1** после Pro-review DRAFT
(`conforms-with-fixes`, `docs/foundation/BA-SDK-ENV-1.1_REVIEW.md`).
Открытые вопросы документа закрываются так:

| Вопрос | Решение |
|---|---|
| O3: лимит «прочих» сообщений | **64 КиБ** на сообщение, кроме `ba:submit` (лимиты EventLog) |
| O3: неизвестные поля | game→host `payload` — strict, неизвестные поля **отклоняются**; `ba:context`/`ba:session` host→game — additive, SDK **игнорирует** неизвестные поля |
| `sessionId`/`session_id` | внешний JSON — `sessionId`; Python/БД — `session_id`; REST §2.23 — `session_id`; конверсия в адаптере; новое решение не создаётся (`OD-FOUND-001`) |
| `clientMeta` | необязательное расширение BA-GAME §6; не влияет на серверные проверки, не хранит PII, входит в лимит 64 КиБ |
| JSON Schema | `schemas/messages/*.json` остаются deliverable этапа 3; до них действуют правила конверта/валидации документа |

**Последствия.**
- SDK/host/player и серверные API используют один конверт
  `{source, protocol:1, type, requestId, sessionId, payload}`.
- Строгий unknown-политика безопасна, потому что платформа контролирует оба
  конца канала; новые поля — только через новую версию схемы.
- `ba-sdk.js` и схемы ещё требуют реализации/актуализации; приёмка документа
  не означает приёмку runtime-среза или продуктовую приёмку App F.
- Публикация/передача документа внешним сторонам не выполнялась.

### D3. BA-ENV-1.1 v1.1.0 — внутренняя приёмка

**Решение.** `docs/contracts/BA-ENV-1.1_v1.1.0.md` принимается как
**внутренний технический контракт окружения и эксплуатации** после
Pro-review DRAFT (`conforms-with-fixes`). Открытые вопросы закрываются так:

| Вопрос | Решение |
|---|---|
| O4: challenge после IP-порога | выбирается **proof-of-work платформы** (без внешнего платного провайдера); до реализации прогрессивного challenge действует **временное ограничение**: `429` после IP-порога. Это не отмена требования Приложения E, а явно помеченный временный режим |
| HSTS | production-значения — по Приложению B ТЗ: `max-age=63072000`, `includeSubDomains=true`, `preload=true`; в dev HSTS выключен. Активация preload — только после реальных доменов/TLS, то есть после внешнего инфраструктурного действия; deploy в этой задаче не выполняется |
| Провайдеры S3/CDN/Sentry/mail | конкретные провайдеры и credentials — внешнее действие; ADR фиксирует только требования и раздельность окружений |
| Digest-политика | digest-pinning базовых образов обязателен для всех окружений; конкретные digest'ы фиксируются при сборке/деплое |
| Redis throttle | отдельный инстанс `redis-throttle` (`noeviction`, без AOF/бэкапа) по `THROTTLE_REDIS_DECISION.md` |

**Замеченное и устранённое расхождение.** Исходный текст §5 BA-ENV v1.1.0
говорил, что `includeSubDomains`/preload не входят в v1.1.0, тогда как
Приложение B ТЗ требует их в production. Приоритет ТЗ: implementation
baseline — значения Приложения B; при внутренней приёмке §5/§11 BA-ENV
приведены к этому решению. Для внутренней разработки без реального TLS
preload не активируется (временное ограничение, а не изменение ТЗ).

**Последствия.**
- Контракт окружения закрыт для планирования и внутренней реализации.
- Production host/домены/TLS/S3/CDN/Sentry/mail остаются внешними
  действиями; никакой deploy, покупка или подключение не выполнялись.
- Временные ограничения (challenge = 429, preload до TLS) должны быть
  сняты отдельными задачами и не выдаются за окончательное поведение.

### D4. Сообщения, unknown-поля и `sessionId`

**Решение.**

1. **Размер.** Прочие сообщения — не более **64 КиБ** фактических байт
   принятого сообщения. `ba:submit` проверяется по лимитам EventLog:
   ≤20 000 событий, ≤2 МиБ raw, ≤256 КиБ gzip. Проверяется фактический
   размер, а не повторная сериализация после парсинга.
2. **Unknown-поля.** Envelope — strict. Game→host `payload` — strict
   (`additionalProperties: false`); неизвестное поле → `E_MESSAGE_INVALID`
   без side effect. Host→game `ba:context`/`ba:session` — additive; SDK
   обязан игнорировать неизвестные поля для совместимости вперёд.
3. **`sessionId`.** Внешний JSON — camelCase `sessionId`; внутренние
   Python/БД поля — `session_id`; REST §2.23 — `session_id`. Преобразование
   выполняется на границе слоя; нормативные примеры ТЗ с `session_id` не
   переписываются. Это применение уже зарегистрированного `OD-FOUND-001`.
4. **`requestId`.** UUID RFC 4122 (v4/v7); LRU на 512 значений на сессию;
   повтор игнорируется; `ba:newSession` очищает LRU. `requestId` не является
   `Idempotency-Key` результата.

**Последствия.**
- 64 КиБ и strict unknown — **внутренние технические параметры контракта**
  (в DRAFT были `[PROP]`); они пересматриваются новой версией схемы, а не
  изменением ТЗ.
- Строгая валидация может отклонять старые игры с лишними полями; это
  осознанная цена контролируемого протокола.
- `clientMeta` не становится доверенным полем и не хранится как PII.
- Новые поля/типы требуют новой версии схемы, а не «молчаливого» расширения.

### D5. App F: доверие, ошибки и verifier

**Решение.**

- Игра, SDK и `clientMeta` — **недоверенные**. Все state-changing операции
  проверяются в Django/БД; host — платформенный посредник, но не источник
  истины.
- `manifest.leaderboard.claimedVerification` — только заявка. `trust_level`
  назначает сервер: `client_reported` (базовый), `heuristic_validated`
  (расширенные проверки), `replay_verified` (успешный серверный replay);
  `server_authoritative` зарезервирован. Клиентский `trustLevel`
  игнорируется.
- Подозрительный результат → quarantine + `SecurityEvent`, не
  автоматический рекорд. Verifier — Python-плагин платформы; replay —
  детерминированный, с серверным seed, timeout 5 с, memory ≤256 МиБ, без
  сети/ФС.
- `ba:error` разрешён в обе стороны; `source` соответствует фактическому
  отправителю; payload `{code, message?}`; `message` нейтральна и
  локализуема, без stack/PII. Ошибка не меняет состояние автоматически.
- Используется полный список 19 кодов §2.23 из BA-SDK §8
  (`E_AUTH_REQUIRED` … `E_INTERNAL`); произвольные коды не добавляются без
  новой версии контракта.

**Последствия.**
- Возможны ложные quarantine и отказы; нужна модерация/CRM-процесс.
- Anti-cheat и `replay_verified` не заявляются как реализованные до
  появления verifier/replay-слоя.
- Ошибки остаются структурированными и безопасными; коды локализуются.

### D6. App F: EventLog

**Решение.**

- Формат: `{"v":1,"seed":"<server seed>","events":[{"t":<ms>,"k":"<kind>","d":{}}]}`.
- `seed` обязан совпадать с `GameSession.seed`; неизвестная версия/schema —
  reject, без «исправления».
- `t` — целые мс от старта, монотонно неубывают, ≤ `durationMs + 1000`.
- `k` — только из `manifest.verification.eventKinds` (≤32); неизвестный
  `k` — reject всего результата.
- `events` ≤20 000; raw ≤2 МиБ; gzip ≤256 КиБ; `d` проверяется
  `verification.eventSchema` (JSON Schema 2020-12) до verifier/replay.
- Транспорт: structured object в postMessage; сервер канонизирует JSON
  (sort keys, без пробелов, UTF-8) и проверяет фактический raw/gzip;
  превышение — `E_PAYLOAD_TOO_LARGE`/`E_MESSAGE_INVALID` без записи.

**Последствия.**
- Игра обязана писать только объявленные события; иначе результат
  отклоняется.
- EventLog нельзя менять при `newSession`; старый лог недействителен.
- Валидатор должен проверять принятые байты, а не только пересобранный JSON.

### D7. App F: storage

**Решение.**

- Один JSONB-документ на `(game, subject_type, subject_id)`; subject — user
  или anon; данные не переносятся между аккаунтами.
- Квота **64 КиБ UTF-8**; ≤256 ключей; глубина ≤8; ключ ≤128; без
  NaN/Infinity; канонический JSON. DB-триггер считает `pg_column_size` как
  страховку и отклоняет >65536 байт; сервис остаётся основным держателем
  UTF-8-квоты.
- API: `GET` возвращает документ и `ETag: "<revision>"`; `PUT` требует
  `If-Match` (`*` или revision); stale/missing → `409 E_STORAGE_CONFLICT`;
  quota → `413 E_STORAGE_QUOTA`; ownership → `403 E_OWNERSHIP`.
- Транспорт SDK — операции по ключу `{op:"get"|"set"|"remove", key, value?}`
  поверх одного документа; SDK публично даёт `get/set/remove(key)`.
- Доступ разрешён после `finished`, но не после `expired/aborted`, кроме
  `newSession`/`exit`. Гостевое TTL — 90 дней с последнего доступа;
  данные сохраняются между версиями игры.
- `capabilities.storage:"local"` в v1 запрещён; storage только через SDK,
  в том числе в opaque-origin режиме.

**Последствия.**
- Клиент обязан обрабатывать 409 и повторять с актуальной revision.
- Гость теряет сохранение по истечении TTL; перенос в аккаунт запрещён.
- Содержимое `data` не сканируется; XSS-ответственность — на рендерящем
  слое SDK. Это остаточный риск, не скрывается.

### D8. App F: leaderboard

**Решение.**

- API: `GET /api/v1/games/{id}/leaderboard?limit=10|100`; default 10,
  maximum 100; TOP-100 на странице портала — с пагинацией.
- Сортировка — по `score.direction`; tie-break — `achieved_at ASC`, затем
  `user_id ASC`. Текущий пользователь всегда виден в таблице; гость
  получает `myRank=null` и в таблицу не входит.
- SDK: `leaderboard.top(n)` — `n ∈ {10,100}`; `leaderboard.myBest()` —
  личный рекорд или `null`. Транспорт — существующий `ba:leaderboard`:
  `{limit?: 10|100, bestOnly?: true}`; ответ `ba:leaderboard:data`:
  - `top` → `{entries:[{rank,nickname,value,achievedAt,trustLevel}], myRank}`;
  - `myBest` → `{value, achievedAt, rank}` или `null`.
  Отдельный тип сообщения не вводится.
- `LeaderboardEntry` связан с `GameResult` композитной проверкой
  (DB-003); пересчёт — в той же транзакции; ручное обновление
  value/achieved_at вне сервиса запрещено.
- Рекорды и результаты не удаляются по времени; только по правилам
  аккаунта/эпохи (§2.11.4).

**Последствия.**
- `myBest` закрыт без расширения Приложения F новым типом.
- `achievedAt`/`trustLevel` обязательны в ответе (дата и бейдж доверия).
- Rank фиксируется на момент submit; последующие результаты его
  устаревают (остаточное поведение, не блокер).

### D10. Retention

**Решение.**

1. **Сроки ТЗ (Приложение D) принимаются как обязательные:**
   - сырые аналитические события — 90 дней, агрегаты бессрочно;
   - `GameSession` — 30 дней;
   - `GameImportDraft` — 7 дней;
   - `GamePlayCredit` — 90 дней;
   - гостевое `GameStorage` — 90 дней с последнего доступа;
   - `AnonymousIdentity` — 90 дней;
   - результаты и рекорды — до удаления аккаунта;
   - исходные ZIP и рабочие бандлы — бессрочно, пока игра существует;
   - `NicknameReservation` — 24 месяца;
   - `SecurityEvent` — 12 месяцев;
   - `AdminAuditLog` — 24 месяца;
   - почтовые логи — 30 дней;
   - бэкапы — 30 дней (RPO ≤15 мин, RTO ≤4 ч);
   - согласия — срок действия + 12 месяцев.
2. **Типы без срока в ТЗ получают временные внутренние значения по
   умолчанию `[PROP]` (обратимые, до юридической/продуктовой проверки):**
   `LoginEvent` — 12 месяцев; `UserGamePlaytime` и `GameRatingVote` — до
   удаления аккаунта/переголосования; `ModerationAction`/`Report` — 24
   месяца; `GameSession.ip_hash`/`ua_hash` — вместе с сессией (30 дней);
   `SecurityEvent.payload` — 12 месяцев; логи приложения — 30 дней.
3. `GameResult`/`LeaderboardEntry` не удаляются по времени; очистка — только
   по правилам аккаунта/эпохи (§2.10.5, §2.11.4).
4. Уже реализованная очистка `AnonymousIdentity`/`AccountToken`/
   `LoginEvent`/`NicknameReservation` сохраняется. Расширение деструктивных
   Celery-задач на другие типы включается после появления моделей и
   проверки. Юридически чувствительные сроки (IP/UA, `SecurityEvent.payload`,
   бэкапы, согласия) остаются временными до юридической проверки; удаление
   персональных данных по ним не расширяется.

**Последствия.**
- Сроки из ТЗ можно реализовывать; `[PROP]`-сроки — **временные внутренние
  значения**, а не утверждение владельца и не нормативное требование.
- GDPR-вопросы (псевдонимизированные IP/UA, удаление из бэкапов,
  `deleted` без субъекта) не закрываются этим ADR.
- `RETENTION_PROPOSAL.md` сохраняет юридические вопросы; удаление
  персональных данных до подтверждения не расширяется.

### D11. Роли, 2FA и step-up

**Решение.**

- Роли CRM — по §2.16: **Владелец**, **Редактор**, **Модератор**,
  **Наблюдатель**. Права реализуются через Django groups/permissions;
  CRM закрыт ролью и 2FA, публичный доступ deny-by-default.
- Все служебные аккаунты — обязательный **TOTP 2FA**, отдельный пароль,
  лимит входа, журнал. 10 одноразовых recovery-кодов (хешируются,
  single-use); офлайн-код восстановления владельца — только superuser,
  журналируется и требует повторного enrollment.
- **Step-up (пароль + TOTP)** обязателен для: смены ролей, публикации,
  удаления игры, смены доменов, экспорта персональных данных, отключения
  2FA, переключения эпохи рекордов, массовых операций. Шаблонное значение
  окна step-up — **15 минут** (технический параметр, временный до
  продуктовой настройки).
- Журнал входов и уведомления о смене ролей/2FA/email обязательны;
  TOTP-секрет хранится в защищённом виде (шифрование/key из env,
  ротация предусматривается).
- `preview/autotest` доступны только из CRM (2FA, роль ≥ Редактор) или
  служебного тестового аккаунта; имперсонация реальных пользователей
  запрещена.

**Последствия.**
- Текущие `PARTIAL`-срезы accounts/2FA не становятся принятыми; ADR
  фиксирует целевую модель и обязательные проверки.
- Реализация ролей/step-up/шифрования — отдельная задача; CRM-экраны,
  E2E staff и security-review остаются.
- Для production юридическая/security-проверка журналов и уведомлений
  остаётся внешней.

### D12. Email-адаптер

**Решение.**

- Все транзакционные письма accounts отправляются через **один внутренний
  адаптер** (`apps/accounts/services/email.py`) поверх Django
  `EmailMessage`/`send_mail`. Прямые вызовы провайдерских SDK из views/
  services запрещены.
- В окружениях используется стандартный SMTP-бэкенд: dev/staging — Mailpit
  (sandbox), production — SMTP-провайдер в ЕС, параметры через
  `EMAIL_HOST/PORT/USER/PASSWORD`, `DEFAULT_FROM_EMAIL`. SPF/DKIM/DMARC —
  требование к провайдеру.
- Bounce: поле `EmailAddress.bounce_at` и сброс подтверждения при
  недоставляемом адресе — требование §2.10.3; приём provider-webhook'ов
  подключается только после выбора провайдера.
- Письма: подтверждение email (TTL 24 ч), восстановление пароля (TTL 30
  мин, одноразовый токен), уведомления 2FA/email. Нейтральный ответ формы
  восстановления сохраняется.

**Последствия.**
- Внутренняя разработка и тесты идут через Mailpit/SMTP без платного
  провайдера.
- Production-email, bounce-webhooks, домен и credentials — внешнее
  действие; без них §2.10.3 не считается принятым.
- Адаптер — единственная точка замены провайдера; это упрощает
  последующую интеграцию.

### D13. Production requirements

**Решение.** Требования BA-ENV-1.1 v1.1.0/ТЗ §2.5 принимаются как
**письменный production baseline**, без выполнения deploy:

| Область | Требование |
|---|---|
| Хостинг | ЕС/ЕЭЗ, 4 vCPU / 8 ГБ RAM / 160 ГБ NVMe; единый хост — известная точка отказа v1 |
| Домены/TLS | портал, отдельный регистрируемый домен игр, wildcard-DNS + wildcard-TLS (DNS-01); `technical_id → host_label`; игры не на поддомене портала |
| Сервисы | `web`, `db`, `redis-cache`, `redis-broker`, `redis-throttle`, `worker`, `beat`, `nginx`, `backup`, `restore-check`; healthcheck, `restart: unless-stopped`, `depends_on: service_healthy`, non-root UID, лимиты |
| Данные | PostgreSQL 18 (pool ≤ max_connections−5), S3 ~100 ГБ + CDN, приватный пакетный bucket и публичный runtime bucket, WAL/PITR |
| Backup/DR | RPO ≤15 мин, RTO ≤4 ч, хранение 30 дней, отдельный провайдер/регион, restore-check; RPO/RTO проверяются учениями |
| Наблюдаемость | Sentry ЕС без PII, JSON-логи с request-id, метрики RPS/латентность/5xx/очередь/БД/диск, uptime 60 с, алерты; TLS-сертификаты и reload Nginx |
| Безопасность | HSTS по ТЗ, CSP, host-only cookies, CSRF, rate limits с субъектом как основным ключом, IPv6 /64, challenge PoW (после реализации), секреты вне Git, digest-pinned images |
| CI/CD | lock-файлы, миграции обратно совместимы, тег → CI → образ → deploy → smoke → откат одной командой |

**Последствия.**
- `compose.prod.yml`/production Nginx/мониторинг/WAL/PITR не считаются
  готовыми: в задаче они только описаны как требования.
- Регистрация доменов, DNS/TLS, хостинг, S3/CDN, Sentry, платные сервисы,
  credentials и production deploy — **внешние действия владельца**; в этой
  задаче не выполнялись.
- Production acceptance остаётся отдельным этапом после внешних действий.

## 2. Сводные последствия и остаточные риски

- Контрактный baseline App F закрыт внутренне: можно реализовывать
  схемы/SDK/CRM/импортёр без выдумывания полей и решений.
- Внутренняя приёмка **не равна** продуктовой приёмке владельца и не
  означает закрытие нормативных этапов 0/1/3.
- Временные ограничения, которые нельзя выдавать за окончательные:
  challenge = `429` до PoW; HSTS preload до реального TLS; step-up TTL 15
  минут; `[PROP]`-сроки retention до юридической проверки; verifier/replay
  пока не реализованы; provider-webhook'и bounce не подключены.
- Внешние блокеры: юридические тексты/версии и GDPR-проверка, email-
  провайдер и bounce-policy, домены/TLS, S3/CDN/Sentry, paid services,
  production deploy, реальный игровой ZIP/лицензии.
- Остаточные технические риски: ложный quarantine, стоимость replay,
  рост idempotency/response JSONB, отсутствие жёсткой ФС-квоты ZIP,
  fail-open throttle, NAT-компромисс 600/ч, stale rank в leaderboard.

## 3. Что этим ADR не сделано

- Не изменялись `technical_specification/` (BA-PLAT-4.2, BA-GAME-2.2) и
  `CLAUDE.md`.
- Не публиковались юридические тексты и не выполнялась их юридическая
  проверка.
- Не подключались платные/внешние провайдеры и не покупались сервисы.
- Не выполнялись регистрация доменов, DNS/TLS, production deploy,
  миграции данных и необратимые операции.
- Не подписывался и не переписывался контракт с игровой командой; реальный
  игровой ZIP не принимался.
- Не выполнялась продуктовая приёмка App F или его отдельных срезов.
