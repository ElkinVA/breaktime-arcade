# BA-GAME-2.2: анализ вариантов A и B для App F

**Дата:** 2026-11-20  
**Статус:** рекомендация технического руководителя; **канонический вариант
не выбран** (решение владельца).  
**Основание:** `docs/audits/BA-GAME-2.2_COMPARISON.md` (машинный diff),
`technical_specification/ts_site.txt` (вариант A, строки 1144–1500),
`technical_specification/ts_game.txt` (вариант B), BA-PLAT-4.2.

Содержательных противоречий между вариантами нет.

## 3. Соответствие архитектуре сайта и App F

Архитектурные инварианты проекта: портал/CRM/API — основной домен; каждая
игра — отдельный origin; игровой код не исполняется в Django; SDK — единственный
канал; `technical_id`/`host_label` immutable; результат и рекорд независимы;
preview/autotest исключаются из агрегатов.

| Требование | Вариант A | Вариант B | Вывод |
|---|---|---|---|
| Origin игры привязан к неизменяемому id | явно (п. 4) | следует из BA-PLAT §2.4.1 | A самодостаточен; B требует платформенного документа |
| Storage только через `ba.storage` | явно (п. 2) + §1–§17 | §1–§17 | functionally эквивалентны |
| Гость: SDK нормализует `E_GUEST_FORBIDDEN` | явно (п. 5) | только BA-PLAT §2.12.5 | A снижает риск неверной реализации Result/SDK |
| Эпохи рекордов | явно (п. 6) | только BA-PLAT §2.11.4 | A снижает риск «удаления таблиц» |
| preview/autotest вне агрегатов | явно (п. 7) | только BA-PLAT §2.18 | A снижает риск загрязнения метрик |
| Manifest-поля 1600/alts | п. 3 + §11 | §11 | эквивалентны по контракту |

Для App F практическая разница сводится к **полноте текста, который читает
разработчик игры**: A содержит явные ответы на вопросы, которые иначе надо
искать в BA-PLAT. Оба варианта одинаково совместимы с серверной архитектурой,
потому что сервер реализует BA-PLAT, а не BA-GAME.

## 4. Интеграция с SDK

- §6/§9 (SDK API, `init/context/ready/submit/leaderboard/storage/newSession/
  exit/fail`, таймауты, совместимость) в A и B идентичны. Разницы интеграции
  SDK нет.
- A явно фиксирует, что гостевая отправка нормализуется SDK и требует SDK 1.1;
  B оставляет это только в BA-PLAT §2.12.5. При выборе B SDK-команда должна
  читать оба документа; при выборе A — достаточно BA-GAME + BA-SDK.
- `capabilities.storage: "local"` запрещён: A повторяет это в блоке решений;
  в §1–§17 обоих вариантов storage уже только `"sdk"`. На API SDK не влияет.

## 5. Интеграция с CRM

- `catalog.description` 1600 и обязательные `coverAlt`/`screenshotAlts` есть
  в §11 обоих вариантов → формы/валидация импорта и approval-UI одинаковы.
- Привязка хоста к `id` (A п. 4) совпадает с текущей моделью каталога
  (`technical_id`/`host_label` immutable) и порядком публикации: CRM не
  пересоздаёт origin при смене названия/локали. B это не повторяет, но и не
  противоречит.
- Эпохи и исключение preview/autotest из агрегатов — одинаково требуются
  BA-PLAT; A делает их явными для CRM-отчётов.

## 6. Проблемы при выборе каждого варианта

**Вариант A:**
- содержит процессную заметку «Следующий шаг» (выдача файлов этапа 1) —
  при публикации как нормы её нужно исключить или явно пометить
  необязательной;
- содержит юридический пункт 8 — он не должен трактоваться как техническое
  требование; остаётся требованием к юридической проверке до запуска;
- выглядит «более нормативным», поэтому есть риск принять его редакционные
  и процессные фрагменты за контракт.

**Вариант B:**
- короче и чище как контракт, но не содержит явных уточнений, которые уже
  действуют в BA-PLAT; разработчик игры, читающий только BA-GAME, может
  пропустить guest-нормализацию, эпохи, запрет storage local и правило
  привязки хоста к id;
- требует обязательной ссылки «см. BA-PLAT §…» для каждого такого пункта,
  иначе возрастает риск расхождения SDK/CRM.

## 7. Рекомендация

**Рекомендую вариант A как канонический** по следующим причинам:

1. A — надмножество B: §1–§17 идентичны, дополнительный блок не противоречит
   платформе и повторяет уже действующие требования BA-PLAT.
2. Для App F A снижает риск неверной реализации критичных мест: origin ↔ id,
   guest-нормализация, эпохи, исключение preview/autotest из агрегатов.
3. Для SDK/CRM A самодостаточен: не требует параллельного чтения BA-PLAT для
   базовых правил интеграции.
4. Юридический и процессный текст легко отделяется: рекомендуется
   опубликовать A с редакционной правкой — убрать заметку «Следующий шаг»
   из нормативной части, а пункт 8 пометить как требование к юридической
   проверке (не runtime-контракт).

Если владелец предпочтёт минимальный текст, B допустим, но тогда BA-GAME
должен содержать явные ссылки на BA-PLAT §2.4.1/§2.4.3/§2.11.4/§2.12.5/§2.18
для перечисленных пунктов.

**Что это меняет в разработке:** ничего в коде; после выбора варианта
фиксируется SHA-256 канонического файла и ссылка в OWNER_DECISIONS. До выбора
агент использует §1–§17 (идентичны в A и B) и BA-PLAT как источник истины.
