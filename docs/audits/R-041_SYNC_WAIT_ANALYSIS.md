# R-041 — анализ синхронного ожидания ZIP-импорта

**Дата:** 2026-11-22
**Задача:** ARCADE-P4 / A3
**Статус:** ANALYSIS COMPLETE — решение: **оставить синхронный путь** для
текущего объёма; async вынесен в условие пересмотра.

## 1. Фактическое поведение

- CRM upload вызывает `import_package()` в HTTP-запросе.
- `extract_package()` пишет source в `zip_uploads/<job>/source.zip`,
  ставит `extract_zip_task` в очередь `zip` и **синхронно** опрашивает
  `COMPLETED.json`/`STATUS.json` с интервалом 0.5 с.
- Таймаут — `ZIP_IMPORT_WAIT_SECONDS=75` (`config/settings/base.py:419`);
  после него web ставит CANCEL и отклоняет импорт с `X_WORKER_TIMEOUT`.
- `zip-worker` работает с `--pool=prefork --concurrency=1`,
  `prefetch-multiplier=1`; один ZIP обрабатывается последовательно.
- Web под Gunicorn имеет `GUNICORN_WORKERS=4` (dev/staging defaults).
- Пока идёт ожидание, занят один web worker; БД-транзакция импорта не
  держится открытой на весь 75-секундный poll (job/черновик сохраняются
  отдельными операциями), но HTTP-соединение и worker заняты.

## 2. Ресурсный эффект

| Ресурс | Эффект | Оценка |
|---|---|---|
| Gunicorn worker | 1 на импорт, до 75 с | 4 одновременных импорта занимают весь web-пул |
| ZIP worker | 1 extraction одновременно | очередь растёт; лимит 50 с на extraction |
| DB connection | короткие операции, не удерживается на poll | нет долгой транзакции |
| Redis | 1 задача + poll marker-файлов | пренебрежимо |
| Память web | source читается в память (≤25 MiB) + staging | ограничено лимитами импорта |

Худший случай: N staff одновременно загружают большие ZIP → N web workers
ждут до 75 с; при N≥4 каталог/CRM для остальных пользователей деградирует.
Очередь `zip` при concurrency=1 сериализует extraction, поэтому 4 импорта
могут занять до 4×50 с, но web ждёт только 75 с и отменяет более поздние —
это осознанный fail-safe, а не зависание.

## 3. Варианты

1. **Оставить sync (выбрано).** CRM-импорт — редкая staff-операция; 75 с
   покрывает extraction 25 MiB при deadline 50 с; отмена и cleanup уже
   реализованы. Нет миграций, API и UX не меняются.
2. Async job + статус в CRM. Требует нового polling UI, фонового
   importer-а, идемпотентного resume, отдельного worker-а и миграции
   статусов. Это архитектурное изменение без доказанной необходимости при
   текущем объёме; риск для P4 выше пользы.
3. Отдельный import-worker. Дублирует web-логику импорта или требует
   вынести importer в worker; меняет ownership БД/файлов и backup-схему.

## 4. Решение

**Оставить синхронный импорт** в P4. Зафиксировать предел:
- один экземпляр `zip-worker` (concurrency 1);
- web-пул 4; одновременно не более 4 импортов, практически — 1–2;
- при росте объёма (например, >10 импортов/час или регулярные 429/таймауты)
  переходить к варианту 2 отдельной задачей с планом и миграцией.

Условия пересмотра: появление внешних загрузчиков, пакетная загрузка,
необходимость импорта без открытого браузера, SLA на постановку в очередь.

## 5. Остаточные риски

- Долгий HTTP-запрос может быть оборван прокси/браузером; задача всё равно
  выполнится, source очистится по TTL, но CRM покажет ошибку загрузки.
- При 4 одновременных импортах новые запросы к web ждут свободный worker.
- Таймаут 75 с меньше суммы 4×50 с при полной очереди; поздние импорты
  отменяются — это документированное поведение, не потеря данных.

## 6. Проверки

Тесты P3/P4: timeout + CANCEL, worker unavailable без fallback, duplicate
import, cleanup после timeout; live P3: job completed в изолированном
worker. Нагрузочный benchmark не проводился и не заявляется.
